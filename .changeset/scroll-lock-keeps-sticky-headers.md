A sticky header no longer scrolls away while a `KunModal`, `KunDrawer`, `KunCommandPalette` or `KunLightbox` is open, or while anything else holds `useBodyScrollLock`. Since 2.31.0 the lock set `overflow: hidden` on both `<html>` and `<body>`. The viewport takes `<body>`'s overflow only while `<html>`'s is `visible` (CSS Overflow 3 §3.1.4), so with `<html>` hidden, `<body>`'s `hidden` applied to `<body>` itself and made it a scroll container. A `position: sticky` element sticks to its nearest scroll container, and `<body>`'s never scrolls, so on a scrolled page the header jumped back to where it sits in the document and left the screen. moyu's topbar vanished behind its mobile menu this way, and the docs site's own header did the same behind every drawer.

The lock now goes on the one element that gives the viewport its overflow, the choice Base UI's `getViewportScroller` makes: `<body>` when `<html>`'s overflow is `visible`, `<html>` otherwise. A `<body>` that already scrolls itself (a full-height app scrolling in `<body>`) is still locked too. Measured in Chromium at 390px and 1280px, on a page scrolled 900px, for pages with no overflow rule, `html { overflow-y: scroll }`, `html { overflow-x: hidden }`, `body { overflow-x: hidden }`, a scrolling `<body>`, and the iOS fixed-body path: the header stays at the top in each case (it was 900px above the viewport on 2.50.0 in all but the scrolling `<body>`), a wheel over the backdrop still does not move the page, and closing puts back the page's own inline styles and scroll position. Nothing changes for consumers.
